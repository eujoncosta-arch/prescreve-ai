# RM-107.1.1-E2.8.1 — Identidade/propriedade ponta a ponta, modo demo/offline, legado e multi-aba

Sem commit, push ou deploy. Motores A/B/C, doses, catálogos e regras clínicas intocados. D1–D14 seguem pendentes. Nenhuma alegação de LGPD, privacidade ou proteção criptográfica: o `localStorage` continua legível por quem tem acesso ao navegador.

## 1. Diagnóstico atualizado
- E2.8 verificava só que o token era aceito (`GET /api/consultas`); o proprietário continuava sendo o `sub` decodificado no navegador. Isso não provava que o servidor reconhece essa identidade.
- Backend não tinha endpoint de identidade.
- Multi-aba: merge por id com "último gravador vence" — uma aba defasada podia sobrescrever ou ressuscitar registros em silêncio.

## 2. Mudanças
| Arquivo | Mudança |
|---|---|
| `backend/src/auth/auth.controller.ts` | `GET /auth/me` (aditivo, somente leitura, `JwtAuthGuard`): devolve apenas `{id,email,perfil}` do usuário que o servidor autenticou (assinatura, expiração, usuário existente e ativo). |
| `frontend/src/lib/api-client.ts` | `verificarSessao()` chama `/auth/me` e devolve `{ok:true,id}`; 2xx sem `id` textual ⇒ `indisponivel`. |
| `frontend/src/lib/store.tsx` | A sessão só é "verificada" se `id` do servidor === `sub` do token. Divergência ⇒ nada restaurado, nada persistido. Aviso (toast) quando a gravação é recusada por conflito entre abas. |
| `frontend/src/lib/pendencias-locais.ts` | Controle de concorrência por registro (`salvo_em` visto por aba): `salvarPendencias` recusa sobrescrever/remover/ressuscitar registro alterado por outra aba e expõe `ultimosConflitos`; `descartar…` limpa o controle da própria aba. |

## 3. Fluxo de identidade
login/registro → tokens → `getCurrentUser()` (sub) → `GET /auth/me` → `id_servidor === sub`? sim ⇒ `identidadeVerificada=sub` ⇒ `carregarPendencias(sub)` / `salvarPendencias(sub)`. O `owner` armazenado no `localStorage` só seleciona registros; nunca prova identidade. Token adulterado (sub≠servidor), 401/403, 5xx, rede/timeout, resposta sem id ⇒ não verificado.

## 4. Matriz de modos de operação
| Modo | Verificação | Restaura | Persiste | Observação |
|---|---|---|---|---|
| Real + servidor OK, id confere | sim | sim (só do próprio dono) | sim | — |
| Real, id do servidor ≠ sub | não | não | não | provado em teste e no navegador |
| Real, 401/403 | não | não | não | falha de auth nunca vira sucesso |
| Real, offline / 5xx / timeout | não | não | não | pendências ficam no disco, só voltam após verificação |
| Demo (`IS_DEMO_MODE`) | nunca consulta servidor | não | não | pendências reais no navegador ficam byte a byte intactas; dado demo nunca é gravado |
| Sem backend configurado | não | não | não | mesmo caminho do demo/offline |

## 5. Legado v1 (sem proprietário)
Análise: o formato v1 não registra dono. Só os registros com `backend_id` podem ser provados (o servidor confirma a propriedade via `buscar`, já implementado em E2.8: "Verificar propriedade no servidor"). Registros sem `backend_id` não têm prova possível ⇒ **permanecem em quarentena** (não exibidos, não enviados, não atribuídos) com descarte explícito e mensagem clara de perda. Nenhuma recuperação automática foi criada, por não ser segura.

## 7. Achados visuais (pré-existentes, não corrigidos — fora do escopo)
- A `Sidebar` tem largura fixa `w-56` sem colapso em telas estreitas: a 375px a coluna de conteúdo fica com ~140px e todo o app (inclusive a nova seção) quebra texto letra a letra. Com a sidebar oculta, a seção nova cabe em 375px sem overflow horizontal.
- A lista "Prescrições emitidas" mostra a pendência local (não confirmada) como cartão com botões Imprimir/PDF e, a 375px, os botões são cortados. Confirma o achado F-5 da E2.7 (rótulos/ações sugerem emissão para algo não confirmado). Requer decisão antes de qualquer mudança.

## 8. Veredito separado R1–R8
| Risco | Veredito |
|---|---|
| R1 sem criptografia | **Aberto, aceito e documentado**: o isolamento é da aplicação, não do disco. |
| R2 órfãos sem TTL | **Aberto**: descarte é manual; política de expiração é decisão do usuário. |
| R3 legado sem `backend_id` | **Mitigado**: quarentena + descarte explícito; recuperação segura impossível. |
| R4 demo/sem backend | **Resolvido**: comportamento explícito, segregado e testado. |
| R5 offline exige verificação | **Resolvido por desenho**: sem prova do servidor nada é restaurado; sem perda (registros ficam). |
| R6 owner forjável | **Parcialmente resolvido**: o dono usado deve coincidir com o id devolvido pelo servidor; quem edita o `localStorage` ainda lê/altera tudo (R1). |
| R7 multi-aba | **Mitigado**: sem sobrescrita silenciosa (aviso e recarga); limitação: se duas abas gravarem no mesmo milissegundo `salvo_em` coincide; não há `BroadcastChannel`/evento `storage` para atualizar a aba defasada automaticamente. |
| R8 outras chaves apagadas no logout | **Aberto**: política FE-03 mantida deliberadamente. |

## 9. Riscos residuais adicionais
- `window.confirm` (logout/descarte) sem teste de UI automatizado.
- Conflito entre abas só é sinalizado; a aba defasada precisa recarregar manualmente.
- Layout mobile geral do app (sidebar) e rótulo "emitida" para pendência local dependem de decisão.
