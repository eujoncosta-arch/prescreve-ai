## 4. Fluxos / pontos NÃO integrados e justificativa

- **Persistência em `localStorage` (favoritos, protocolos, consultas pendentes) e backend:** fora de escopo. Para isso o registro é removido: `semRegistroParaPersistir` antes de gravar favoritos e antes de `UPDATE_PRESCRIPTION` (o store grava consultas pendentes no `localStorage`). O payload do backend é montado campo a campo e não é afetado.
- **Favoritos/protocolos lidos:** não foram alterados; itens sem registro são interpretados como `nao_avaliada` via `registroEfetivo()`. Favoritos já gravados e novos nunca contêm registro (efeito: ao reaplicar um favorito, a avaliação anterior **não** é recuperada — comportamento desejado nesta etapa).
- **Impressão, rótulos, cores e mensagens:** não tocados.
- **`PrescriptionPanel` e `store`:** o registro vive só no estado local do Panel; a consulta ativa no store não o recebe.

## 5. Decisões e pontos a revisar

1. **Origem de `addToRx`:** o prompt permite `digitada_pelo_prescritor`. Na prática a dose desse caminho vem pré-preenchida pelo catálogo/`calcWeightDose` e é editável; não é possível distinguir "digitada" de "pré-preenchida". Marquei como `campos_padrao`: `via`, `frequencia`, `duracao`; a dose **não** foi marcada como padrão para não afirmar o que o código não sabe. Pendente de decisão se deve haver origem própria.
2. **`comEdicaoManual` (E1) só é usado para avaliados.** Para `nao_avaliada` evitei o rebaixo do motivo para `editada_apos_calculo` (nada foi calculado antes). E1 não foi modificado.
3. **Teste do literal `itens: rxItems,` (RM-105.2.1):** minha primeira versão alterava essa linha e quebrou o teste; **não alterei o teste**, adaptei o código (o registro é removido em `const updated`, mantendo o literal).
4. `types.ts` usa `import('./dose-contract/registro')` em posição de tipo para evitar dependência circular de módulos.
