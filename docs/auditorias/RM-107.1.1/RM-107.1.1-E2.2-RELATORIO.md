## 1. Verificação de compatibilidade do backend (antes de implementar)

- `ItemMedicamentoDto` (backend): `molecula`, `dose: DoseEstruturadaDto` (obrigatório, validado), `duracao`, `observacoes?`. `main.ts`: `whitelist + forbidNonWhitelisted` ⇒ **campo extra = 400**.
- `store.tsx` monta o payload campo a campo (`molecula`, `dose`, `duracao`, `observacoes`) a partir de `dose_estruturada`; item **sem** `dose_estruturada` já é barrado antes da rede (`sem_dose_estruturada`, sem chamada ao backend).
- **Achado:** o texto livre `posologia` **nunca** é enviado ao backend (pré-existente). Logo, "preservar o texto" só é possível localmente; o backend nunca teve o texto.
- Conclusão: com o contrato atual é possível impedir o envio do DTO antigo **sem** campo novo e **sem** alterar o backend, usando o gate existente. Não foi preciso interromper o fluxo de gravação nem criar workaround.

## 2. Implementação

| Requisito | Como |
|---|---|
| Detectar edição posológica | `registrarEdicaoPosologica` (E2/E2.1): `dose`, `unidade`, `frequencia`, `via`, `posologia`, `concentracao`, `medicamento`, `molecula` marcam o DTO como divergente; `duracao`/`quantidade`/`forma`/`uso_continuo` só invalidam a avaliação |
| Invalidar avaliação | já existente (E2): `comEdicaoManual`/trilha; nada promovido |
| Marcar DTO como desatualizado | `dose_divergente` no registro (E2.1) + `doseEstruturadaDesatualizada(item)` |
| Impedir envio | `prepararItemParaStore(item)`, chamado no `handleFinalize` do `PrescriptionPanel`: remove o registro (memória) e, se o DTO está desatualizado e não reconfirmado, **omite `dose_estruturada` do item enviado ao store** ⇒ o gate de sincronização existente bloqueia a prescrição (`sem_dose_estruturada`) e nada chega ao backend |
| Não recalcular/reconstruir | nenhum código calcula DTO; o anterior só é copiado/restaurado |
| Reconfirmação explícita | `reconfirmarDoseEstruturada(reg)`: ação do prescritor (botão "Reconfirmar dose estruturada anterior"); restaura o **mesmo** DTO |
| Reconfirmação ≠ validação | a avaliação permanece `nao_avaliada`; `homologacao_clinica:false`; histórico em `reconfirmacoes_dose` e na trilha `edicoes_manuais`; aviso na tela "A reconfirmação não valida clinicamente a dose." |
| Edição pós-reconfirmação | DTO volta a ser desatualizado (testado) |
| Texto original e histórico | `texto_original`, `edicoes_manuais`, `dose_divergente.dose_anterior`, `reconfirmacoes_dose` (memória do Panel) |

## 6. Limitações e riscos

1. **Efeito prático do bloqueio:** a prescrição com DTO desatualizado não reconfirmado **fica local** (sync `sem_dose_estruturada`), como já ocorre com qualquer item sem dose estruturada. A mensagem do store ("confirme a dose manualmente") é a pré-existente; **não existe tela, após finalizar, para reconfirmar** — a reconfirmação só é possível no Panel, **antes** de finalizar. Corrigir isso exige UI no fluxo pós-finalização (etapa própria).
2. **Mudança visível:** foi acrescentado um aviso e um botão no `PrescriptionPanel` e um toast na finalização. É a única forma de a reconfirmação ser "explícita" pelo prescritor; as restrições desta etapa não proibiam UI, mas é uma alteração de interface e deve ser revisada.
3. O texto `posologia` editado **não é enviado** ao backend (pré-existente); o histórico (texto original, edições, reconfirmações) existe só em memória enquanto o Panel está aberto — ao finalizar o registro é removido.
4. A reconfirmação reabilita o DTO **antigo**, sem comparar com o texto: é uma declaração do prescritor, não uma checagem automática. Não há como validar a correspondência sem interpretar o texto (não feito, para não inventar valores).
5. A `/prescricao-rapida` não possui DTO estruturado nem fluxo de envio: não afetada.
6. P-01, P-04, P-05, P-06, P-08, P-09, P-10 e rótulos verdes (D13) seguem ativos.
