## 0. Errata ao relatório da RM-107.1.1-C
O relatório C afirmou que o backend "descartaria" campos extras (`whitelist`). Verificação: `backend/src/main.ts` usa `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, forbidUnknownValues: true })` ⇒ um campo extra (ex.: `avaliacao`) em `POST /prescricao` seria **rejeitado com erro 400**, não descartado silenciosamente. A conclusão (backend não aceita metadata hoje) permanece; a consequência é mais restritiva. Além disso, `Prescricao.hash_integridade` é um SHA-256 calculado no servidor sobre o objeto recebido (`hashIntegridade(obj)`), portanto qualquer campo novo altera o hash.

## 3. Perdas de informação identificadas
1. **Estado de avaliação** (`estado_avaliacao`/`estado_regra`): existe em F1 e no `FullDoseResult` (RM-107.1.1-A) mas **não passa** a nenhum destino persistente ou impresso.
2. **Alertas e limites excedidos** do cálculo: só o 🚨 influencia o botão; nada acompanha o item.
3. **Limitações** (regra não validada, apresentação não ajustada, regra pediátrica não utilizada): ficam na tela do cálculo.
4. **Origem do número** (cálculo × texto de recomendação × digitado × protocolo × backend legado): inexistente em todos os destinos.
5. **Edição manual posterior** (F3c): não é detectada nem registrada.
6. **Valores padrão não clínicos** (`'Comprimido'`, `'30 comprimidos'`, `'30 dias'`/`'7 dias'`, `'Uso contínuo'`, via adulta, `frequencias[0]`): entram no item sem marca.
7. **Versão** do motor/regra/schema que produziu o dado: inexistente.
8. **Backend**: o DTO e o hash de integridade **não aceitam** metadata.

## 5. O contrato novo atende aos fluxos reais? (análise de `converterDoseComMetadata`)
**Atende:** F1 completamente (DTO + estado da regra/apresentação, alertas, bloqueios, limites excedidos, limitações, dados ausentes, candidatas, origem da regra, `homologacao_clinica=false`, rebaixamento de "validada" sem prova, serialização idempotente, tolerância a metadata ausente).
**Não atende (lacunas reais):**
1. **Entrada exclusiva `DoseResult`**: F2, F3, F3b, F3c, F4, F5, F7, F8, F9 **não têm `DoseResult`**. É preciso (a) **adaptador `FullDoseResult` → metadata** (F3) e (b) **registro "não avaliado"** para texto/legado.
2. **Vocabulários de estado diferentes**: `FullDoseResult.estado_avaliacao` (8 valores, motor C) × `DoseResult.estado_calculo` (7) × `estado_regra` (4) × metadata. Sem tabela de mapeamento, o mesmo fato teria nomes distintos.
3. **Origem do dado** (`texto_livre`, `digitado`, `calculado pelo motor C`, `contrato`, `protocolo`, `backend legado`) não existe na metadata atual.
4. **Edição posterior**: sem marcador de que o valor foi alterado após o cálculo.
5. **Valores padrão**: sem lista de campos preenchidos por padrão.
6. **Versão**: `versao_metadata` existe, mas não há versão do **registro persistido** nem do **motor/regra** (data).
7. **Aprovação formal**: não há registro de aprovações; "validada" só poderia existir com ele.
**Estados que devem ser `desconhecido`/`nao_avaliado` nas origens antigas:** estado do cálculo, estado da regra, apresentação, alertas, limites, limitações, origem da regra, motor/versão. **Campos que não existem nas origens antigas:** todos os de avaliação.
**Incompatibilidades front × backend:** DTO com `forbidNonWhitelisted` (campo extra ⇒ 400); `hash_integridade` sobre o payload; limite de corpo de 1 MB; `Prescricao.medicamentos` é `Json` (comporta o campo, mas o DTO precisa declará-lo); a `dose` do DTO é validada por enum de unidade/frequência.

## 6. Proposta arquitetural única — *Registro de Posologia com Proveniência*
**Princípio:** a dose numérica **nunca** viaja sozinha; ela é parte de um registro que contém sua proveniência e sua avaliação (ou a declaração explícita de que **não foi avaliada**). Para registros antigos, o estado é **`nao_avaliado`** — nunca reconstruído, nunca promovido.

```ts
// Esqueleto de ESPECIFICAÇÃO (não implementado)
type OrigemDaPosologia =
  | 'contrato_dose'            // DoseResult do contrato unificado
  | 'dose_calculator'          // FullDoseResult (motor C), com estado_avaliacao/limitacoes
  | 'recomendacao_texto'       // plano_terapeutico (texto livre) — F2
  | 'digitada_pelo_prescritor' // inclusão/edição manual — F3b/F3c
  | 'protocolo_texto'          // SmartProtocol / favorito legado — F4/F5
  | 'backend_legado'           // registro recuperado sem metadata — F7
  | 'importacao_localstorage'; // F9

type AvaliacaoPersistida =
  | { tipo: 'avaliada'; metadata: MetadataAvaliacaoDose }          // RM-107.1.1-C
  | { tipo: 'avaliada_motor_c'; estado: EstadoAvaliacaoDose; estados_adicionais: EstadoAvaliacaoDose[]; limitacoes: LimitacaoDose[]; fonte_calculo: FullDoseResult['fonte'] } // F3
  | { tipo: 'nao_avaliada'; motivo: 'texto_livre' | 'legado_sem_metadata' | 'editada_apos_calculo' | 'origem_desconhecida'; homologacao_clinica: false };

interface PosologiaRegistrada {
  versao_registro: 'posologia-1';
  dose: DoseEstruturada | null;               // numérico (pode ser nulo se só havia texto)
  texto_original?: string;                    // o que o usuário/receita viu
  origem: OrigemDaPosologia;
  avaliacao: AvaliacaoPersistida;             // OBRIGATÓRIA
  campos_padrao: string[];                    // ex.: ['forma_farmaceutica','duracao','via'] preenchidos por padrão
  edicoes_manuais: Array<{ campo: string; de: string; para: string; em: string }>;  // trilha; qualquer edição ⇒ avaliacao passa a nao_avaliada('editada_apos_calculo') (sem apagar a avaliação anterior, que fica em `avaliacao_anterior`)
  criado_em: string; motor_versao?: string;
  homologacao_clinica: false;
}
```
**Regras da arquitetura**
1. **Gate de tipo (anti "somente DTO"):** APIs de leitura/gravação aceitam `PosologiaRegistrada`; a obtenção do DTO nu exige função explicitamente nomeada (`somenteDtoNumerico(...)`) que retorna também a marca de avaliação — não há atalho silencioso. A conversão legada permanece `@deprecated`.
2. **Mapeamento de estados** documentado e testado (tabela única entre `EstadoAvaliacaoDose`, `estado_calculo`+`estado_regra` e a metadata).
3. **Legado explícito:** leitura de favoritos/backend/protocolos cria **em memória** `{ avaliacao: { tipo: 'nao_avaliada', motivo }, origem }`; **não reescreve** o armazenamento nem infere estado (sem migração silenciosa); a gravação em novo schema só ocorre por ação explícita do usuário.
4. **Edição manual** invalida a avaliação anterior (marca `editada_apos_calculo`), mantém a trilha e **não recalcula**.
5. **Padrões marcados** (`campos_padrao`) e exibidos como "não informado/padrão".
6. **Backend (aditivo e versionado):** `ItemMedicamentoDto` ganha `avaliacao?` e `origem?` opcionais, declarados e validados (shape, tamanho, `homologacao_clinica === false`; **rejeitar `regra_clinicamente_validada` enquanto não existir registro de aprovação** no servidor); persistência dentro de `Prescricao.medicamentos` (Json, sem mudança de schema) **ou** campo próprio — decisão de governança; `hash_integridade` passa a cobrir a avaliação em campo de hash separado ou versão de hash declarada (para não invalidar registros existentes). Registros antigos: ausência ⇒ `nao_avaliada('backend_legado')` na leitura.
7. **Exibição neutra** do estado nos lugares onde a dose aparece (cálculo, lista da receita, `/prescricoes`, impressão do paciente/anexo): texto informativo, sem verde/selo (a redação final depende de **D13**).
8. **Versionamento:** `versao_registro`, `versao_metadata`, `versao_conversao`, schema dos favoritos (`prescreve-ai-favoritos` v2) e do DTO.
9. **Nenhuma política clínica nova:** o registro só descreve; bloquear/exigir confirmação continua em D1/D2/D7.
