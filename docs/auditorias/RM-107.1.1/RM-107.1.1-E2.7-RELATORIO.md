## 2. Arquitetura consolidada e fluxo de dados/estados
```
Plano/Recomendação (F2) ─┐
Inclusão manual (F3b)  ──┼─► PosologiaRegistrada (memória: origem, trilha, dose_divergente, reconfirmacoes_dose)
Motor C (/rápida, F3)  ──┘        │ edição ⇒ avaliação invalidada; campo do DTO ⇒ dose=null + dose_divergente
                                  ▼
                 posologia-consistencia.avaliarIntegridadeDto  (ÚNICA política)
        consistente_conforme_origem │ divergente │ nao_verificavel │ estrutura_indisponivel
                                  ▼  prepararItemParaStore  (remove registro; divergente ⇒ bloqueio_dto + DTO preservado; envelope prov-1)
                 store (UPDATE_PRESCRIPTION) ──► localStorage pendentes (item + bloqueio_dto + proveniencia; NUNCA registro/trilha)
                                  ▼  executarSincronizacaoConsulta  (ÚNICO chamador de criarPrescricao)
   gate 1: bloqueio_dto ⇒ NÃO envia │ gate 2: sem dose_estruturada ⇒ NÃO envia │ payload = {molecula,dose,duracao,observacoes}
                                  ▼  POST /api/prescricao  (idempotency_key, DTO validado)
   ConsultaService: consulta do usuário → busca por chave → escopo → fingerprint (409 se conteúdo difere) → $transaction(create+auditoria) → P2002 ⇒ vencedora + fingerprint
                                  ▼  PostgreSQL (unique idempotency_key; coluna idempotency_fingerprint nullable)
 Estados de sync por prescrição (classificarSincronizacaoPrescricao): sem_prescricao_local │ somente_no_dispositivo │ bloqueada_por_integridade │
   aguardando_sincronizacao │ sincronizando │ falha_de_rede │ falha_de_servidor │ envio_interrompido │ sincronizada │ desconhecido
 Recuperação: /prescricoes → itemParaRevisao (origem original restaurada do envelope) → reutilização explícita → REVIEW_PRESCRIPTION → reenvio manual
```

## 4. Verificações pedidas (resultado independente)
**Posologia:** (1–2) estados coerentes; impossíveis tratados: `bloqueio_dto`+registro ⇒ divergente; `dose`+`dose_divergente` ⇒ `dose` descartada; `vigente` forçado `false` se divergente. (3) edição invalida avaliação (`editada_apos_calculo`/trilha) — testado. (4) recuperação preserva origem original quando o envelope é legível — testado; **sem envelope ⇒ `conhecida:false`**, nunca inventada. (5) declaração do prescritor é bloco separado e não altera a avaliação (`nao_avaliada`). (6) **nenhum** caminho transforma dose não avaliada em validada (varredura do código: nenhum construtor produz `regra_clinicamente_validada`; testes e2 a e25). (7) **Caminhos alternativos:** `consultaApi.criarPrescricao` só é chamada em `store.tsx` (dentro de `executarSincronizacaoConsulta`); `dose_estruturada` só é lida em `store` e nos módulos de posologia; reducers `UPDATE_PRESCRIPTION`/`REVIEW_PRESCRIPTION` **não impõem** a política (dependem do chamador — hoje corretos). (8) proveniência preservada nos fluxos Panel→finalização→persistência→revisão; **perdida** em: sessão expirada (F-1), favoritos/protocolos (por desenho) e `/prescricao-rapida` (não sincroniza).
**Consistência DTO × conteúdo enviado:** o payload usa `molecula=item.medicamento`, `dose=DTO`, `duracao`, `observacoes`; editar `medicamento/dose/frequencia/via/posologia/concentracao` invalida o DTO ⇒ **não há como enviar DTO que difira do que o prescritor vê** sem reutilização explícita.

**Sincronização — distinção de estados**
| Situação | Distinguida? |
|---|---|
| Ainda local / sincronizando / sincronizada | Sim (`aguardando`/`somente_no_dispositivo`, `sincronizando`, `sincronizada` só com 2xx real) |
| Falha transitória (rede/timeout/5xx/interrompida) × definitiva (4xx, **409**) | Sim (`error_kind`; 409 ⇒ `falha_de_servidor`, `pode_reenviar:false`) |
| DTO divergente | Sim (`bloqueada_por_integridade`) |
| **Registro sem estrutura numérica** | **Não (F-4)** — sonda: `{"estado":"aguardando_sincronizacao","detalhe":"O bloqueio de integridade anterior foi resolvido por revisão…","pode_reenviar":true}` para um item sem DTO e sem marcador |
| **Legado não verificável** | Só no nível do item (política); **não** aparece no estado de sincronização |
Nenhum erro de transporte é apresentado como sucesso (testado); a exceção é o rótulo falso de F-4 (não é sucesso, mas descreve incorretamente o bloqueio).

**Backend/persistência:** timeout durante escrita ⇒ 500 em `query_timeout` (E2.6); **COMMIT ambíguo** ⇒ resolvido por repetição com a mesma chave (testado: resposta perdida, reinício do app/PostgreSQL, queda durante 40 escritas); repetição igual ⇒ mesmo registro; diferente ⇒ **409**; legado/fingerprint nulo/ilegível ⇒ derivado ou comportamento legado (sem afirmar igualdade/divergência); **0 duplicações e 0 sucessos falsos** nos cenários executados. Idempotência **não** ampliada a outras entidades.

## 12. Pendências que bloqueiam o RM-107.3 (shadow mode)
**Bloqueiam:** (a) **F-1 e F-3** — não ampliar o uso do fluxo de prescrição enquanto houver perda silenciosa e PHI sem escopo de usuário; (b) **F-4/F-7** — estados de sincronização/estrutura precisam ser verdadeiros antes de qualquer comparação ou exibição baseada neles; (c) **D1–D14** (decisões clínicas) e **D13** (rótulos) — o shadow mode não pode decidir regra clínica nem rótulo; (d) decisão sobre `nao_verificavel` (F-6).
**Não bloqueiam (recomendados):** F-2, F-8, F-9, F-10, fingerprint para outras entidades.

## 13. Critério de encerramento
Não há perda de proveniência **no fluxo normal**, bypass do bloqueio, duplicação de prescrições nem inconsistência DTO × conteúdo enviado — **mas** F-1 (perda na expiração de sessão) e F-3 (sem escopo de proprietário) são achados altos reais, e F-4 é um estado falso. Por isso o conjunto **não é declarado “pronto para integração sem ressalvas”**: o E2.6 está pronto para integrar; o restante exige as RMs da §10. Aprovação **exclusivamente técnica** (não é validação clínica nem autorização de uso clínico autônomo).
